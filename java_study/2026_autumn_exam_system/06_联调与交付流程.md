# 联调、Git 与最终交付

当前阶段为规划文档入仓。后续还须实现业务、完成真实联调并将成功/失败/异常案例保存到 Apifox，不能把规划入仓视为项目验收完成。

## 先分工并冻结接口

你负责后端业务、数据库、接口说明与后端案例。前端同学负责教师/学生页面、表单交互、调用接口、错误提示。两人一起确认题型、字段、成绩口径、状态、Cookie/代理和错误响应。

第一天先交给队友 [接口约定草案](04_接口约定.md)，按页面逐条核对。任何接口调整先同步示例和文档，再改双方代码。约定的最小事项包括：

- 请求方法、路径、字段类型和必填规则。
- 成功 JSON、失败 HTTP 状态与业务 code。
- 时间格式、分页起点、分数/总分和 null 的含义。
- 登录态、CSRF Token 和前端代理配置。
- 哪位同学负责修改与验证，何时可联调。

每天至少同步一次：已完成且验证的功能、接下来要改的接口、当前阻塞、对方需要配合的事项。用具体请求和错误信息沟通。

## Mock.js 和真实接口如何衔接

Mock.js 适合前端根据同一份接口结构生成列表、空数据和错误情形，使页面开发不必等待后端每个接口完成。[Mock.js 官方仓库](https://github.com/nuysoft/Mock) 对其定位是模拟数据和请求响应工具。

前端有余力时加入模拟数据；后端优先完成 MySQL 上的真实业务接口。切换真实联调时关闭会拦截同一路径的 Mock，确认浏览器请求的确到达 Java 服务。

至少检查：正常列表、空列表、加载中、参数错误、登录失效、没有权限、服务器异常。判断成绩的依据来自后端响应，不能在前端模拟一份固定成绩当作已联调。

## Apifox 交付要求

1. 建立团队项目，按登录、个人资料、教师、学生考试、成绩历史分组。
2. 导入后续生成的 OpenAPI 文档，对照实际接口修正；本次 Markdown 不是已上传的 Apifox 文档。
3. 设置本地环境 baseUrl；准备相互隔离的教师、学生会话并保持 Cookie。
4. 每条写入请求按约定获取/携带 CSRF Token。
5. 保存成功、业务失败、格式/资源/服务异常三类案例。最低集合见 C01–C22。
6. 记录实际请求、响应、数据库核对信息。不要在公开文档或截图里保留个人密码、有效 Cookie、令牌和真实个人资料。
7. 前端逐页切换真实接口，双方共同完成一轮教师/学生流程；组长按自己的环境能复现。

没有前端队友时，按通知在 Apifox 演示真实流程：教师登录和出题 → 学生登录和考试 → 判分 → 重考 → 教师查历史。提前与组长确认这类队伍的展示安排。不要默认它等同于“有前端组已经完成页面联调”。

## Git 工作方式

先理解你给的分支文章：正式版本、集成开发和单项功能分开管理。分支策略原作者也强调按团队交付方式选择复杂度，[原始说明](https://nvie.com/posts/a-successful-git-branching-model/) 不把一套模式视为通用规则。若工作室详细规范有明确要求，优先遵循其规范。

本项目后续建议：

| 分支 | 作用 | 合并时机 |
|---|---|---|
| main | 能按 README 运行的答辩版本 | 功能及联调检查完成 |
| develop | 前后端集成 | 单项功能通过自测后合入 |
| feature/backend-auth 等 | 一个相对独立的功能 | 检查改动、接口与案例后合回 develop |
| fix/submit-duplicate 等 | 修复一个清楚的问题 | 复现问题并验证修复后合回 develop |

可用前缀 feature/frontend-exam、feature/backend-question、feature/backend-exam 区分工作。小组长若要求简化为 main + 功能分支，按小组约定调整。初版不机械增加 release/hotfix 全套流程。

提交信息使用 `<type>(<scope>): <description>`，scope 可选。规范依据是 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)。例如：

```text
feat(auth): 增加教师和学生登录
feat(question): 实现课程题目增删改查
feat(exam): 保存试卷快照并完成服务端判分
fix(exam): 防止重复交卷覆盖成绩
test(exam): 增加重考和越权访问案例
docs(api): 更新交卷失败响应说明
refactor(grade): 拆分判分与数据库保存逻辑
chore(build): 配置 Java 8 编译参数
```

一次提交围绕一个能说明的变化，先检查差异和相关测试。IDEA 的提交插件只是帮助填写格式，掌握规范后可以直接填写，不把安装插件作为开工条件。你提供的插件文章未能完整读取，因此没有指定或安装某个插件。

## 发布前交付候选清单

| 内容 | 验收标准 |
|---|---|
| 后端源码与 pom.xml | JDK 8 下构建成功，依赖版本明确 |
| 前端源码（有前端组） | 启动说明、后端地址配置、真实接口流程可运行 |
| 数据库脚本 | 可在空的独立 MySQL 库初始化，不在应用重启时自动清数据 |
| 演示数据 | 虚构教师、学生、课程、题目；能覆盖重考与权限场景 |
| 配置说明 | 数据库地址/用户名/密码的填写位置清楚，真实凭据不公开 |
| README | 项目功能、版本、启动步骤、初始化步骤、演示流程、已知边界 |
| Apifox | 团队文档真实保存，组长可以查看成功/失败/异常案例 |
| 测试证据 | 判分、历史、越权、重复请求、回滚等有实际结果 |
| 亮点说明 | 指向实际代码和测试，写清解决的问题和限制 |
| GitHub public | 由你安排发布后核验可公开拉取，并从干净环境复现 |

部署上线是通知中可按情况优化的后续工作，五天先把本地真实流程、解释能力和必需交付做好。未部署就如实说明运行环境。
