# 需求、默认规则与验收

本项目范围为在线考试系统，包括教师端题库与成绩管理、学生端答题与重考，以及前后端联调和接口交付。公开注册、强制倒计时、聊天和大模型调用不纳入当前版本。

## 明确要求与验收证据

下表定义验收标准。R01–R10 已实现后端代码，并通过自动化与 HTTP 验证，详情见 [TESTING.md](TESTING.md)。R11 的前端页面联调、R12 的团队 Apifox 导入/保存，以及 R13 的业务代码发布尚待完成；本地测试不代替这些交付步骤。

| 编号 | 必须实现的功能 | 验收证据 |
|---|---|---|
| R01 | 登录后区分教师端与学生端 | 教师与学生分别登录；响应角色正确；学生访问教师接口被拒绝 |
| R02 | 教师信息：姓名、性别、手机号、工号、学院、教授课程 | 教师个人信息接口和页面字段完整，教授课程来自课程关联 |
| R03 | 教师看到课程及其中全部题目，能增删改查题目 | 新增题目后查到，编辑后变更，删除后列表不再显示 |
| R04 | 教师看到考生姓名、科目、成绩、考试时间等 | 真实交卷后，在教师端查到对应记录 |
| R05 | 同一学生同一课程重考多次，展示每次成绩 | 学生完成两次考试，教师能查看两次不同答卷及时间 |
| R06 | 学生查看并修改、保存个人信息 | 修改后重新查询或重新登录，资料仍保存在数据库 |
| R07 | 学生看到所选课程并开始答题 | 已选课程能进入考试，未选课程不能通过改参数进入 |
| R08 | 提交答案，由服务端批改、保存并返回成绩 | 前端只交答案；数据库有结果；修改客户端分数无法影响成绩 |
| R09 | 课程显示考试状态与成绩，已考后不能直接再考 | 提交后显示成绩，普通开始请求被拒绝并提示重考 |
| R10 | 明确点击重考后可以再次考试，旧成绩保留 | 重考产生新答卷，旧答卷、旧成绩不被覆盖 |
| R11 | 有前端的组完成真实前后端互通 | 浏览器中的真实请求到达后端，MySQL 中对应数据发生变化 |
| R12 | 接口文档保留在 Apifox，包含成功、失败、异常案例 | Apifox 项目里有实际保存的接口、请求数据与响应示例 |
| R13 | 项目保存在公开 GitHub 仓库 | 业务代码发布后可从干净目录按 README 启动，仓库可公开访问 |

“失败”包括业务规则拒绝，如已考后普通开始；“异常”包括格式错误、资源不存在、数据库故障等。不能仅保存一种 200 成功响应。

## 待确认的业务规则

下列事项是本版采用的默认规则，不是原要求中已经明确的全部细节。前后端仍需共同确认；需求变更时同步修订接口和数据库方案。

| 未明确事项 | 当前默认 | 修改会影响什么 |
|---|---|---|
| 题型 | 四选一单选题，支持逐题分值 | 多选、填空、主观题会增加校验、判分和页面复杂度 |
| 试卷组成 | 一门课程当前全部有效题目，按固定顺序出卷，最多 1000 题 | 随机组卷或超大试卷需要额外规则 |
| 账号来源 | 预置演示教师、学生账号；不增加公开注册功能 | 若要求注册，需要新增注册与角色分配流程 |
| 课程与选课 | 课程、教师关系、学生选课关系预置 | 自主选课或课程增删改需要新增接口与页面 |
| 教师范围 | 每门课一位教师，只能管理自己的课程 | 多教师共同授课需要关联表与权限调整 |
| 学生资料修改 | 姓名、性别、手机号、学院可改；学号、角色不可改 | 身份信息更改需要额外规则 |
| 教师资料 | 必须能展示；可复用同一资料修改接口 | 不新增教师管理后台 |
| 考试时间 | 记录开始、交卷时间，无强制限时 | 倒计时、超时交卷属于额外功能 |
| 重考次数 | 不限次，但必须通过重考动作开始 | 次数限制会改变状态判断 |
| 成绩口径 | 返回实际得分和卷面总分；课程显示最近一次已交卷成绩 | 最高分、百分制换算需另定展示规则 |
| 未完成答卷 | 再次打开返回同一张进行中的答卷 | 暂不承诺退出后保留尚未提交的选项 |
| 未答题 | 按零分处理，仍允许交卷 | 强制全部作答需要额外提交校验 |
| 成绩查看范围 | 学生只看自己的；教师只看自己课程的 | 不提供全站成绩查询 |

演示数据建议使用两名教师、三名学生、三门课程；其中两门有题，一门空题。至少一名学生选两门课、一门课有两名学生，方便验证关系和权限。全部使用虚构信息。

## 三个关键流程

教师流程：登录 → 查看个人信息及教授课程 → 打开课程 → 新增/查看/编辑/删除题目 → 查看该课程考生成绩 → 查看某学生的历次成绩。

学生流程：登录 → 查看及修改个人信息 → 已选课程列表 → 开始考试 → 选择答案 → 提交 → 查看得分和总分 → 返回课程列表看到状态 → 点击重考 → 再提交 → 历史出现第二次记录。

两端联调流程：约定接口和示例 → 前端用模拟数据完成页面 → 后端在 MySQL 上通过 Apifox 验证 → 前端切换到真实接口 → 完成上述两条流程 → 保存成功、失败和异常案例及测试记录。

## 状态与按钮约定

| 后端状态 | 含义 | 前端可显示的动作 |
|---|---|---|
| NOT_TAKEN | 没有进行中答卷，也没有已交卷记录 | 开始考试 |
| IN_PROGRESS | 有一张进行中的答卷 | 继续考试 |
| COMPLETED | 没有进行中答卷，已有已交卷记录 | 查看成绩、重考 |

课程状态由答卷记录计算，不在前端自行永久保存。若正在重考，状态为 IN_PROGRESS，同时可以展示上一次已交卷成绩。COMPLETED 只是课程列表的展示状态，答卷表本身使用 IN_PROGRESS / SUBMITTED。

## 优先级

P0：R01–R10 完整功能、R11/R12 可验证的联调与接口证据、基本异常处理。用户身份校验、后端判分、历史不覆盖是核心业务正确性的一部分。

P1：防重复交卷、题目快照、分页和筛选。在核心功能中逐步落实，并提供对应测试证据。

P2：错题回顾、统计图表、限时考试、Excel 导入、复杂题型等。仅在核心流程通过验收后考虑。Redis、微服务、消息队列不纳入当前版本。
